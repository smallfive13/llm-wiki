# Wiki Schema

知识库结构、字段、契约的高密度参考。Agent 会话开始时优先读本文件。

更详细规范请到当前 llm-wiki 引擎仓查找以下文件：

- `AGENTS.md`
- `wiki-design/01-architecture.md`
- `wiki-design/05-contracts-and-next-steps.md`
- `wiki-design/04-agent-rules.md`

引擎仓路径来源：通过 wiki skill 使用实例时来自 skill 配置 `instances.json` 的 `engine` 字段；直接运行引擎脚本时即 `scripts/wiki_init.py` 所在的仓库根。

## 目录结构

```text
knowledge/
├── purpose.md / index.md / overview.md / log.md     # 上下文层（无 frontmatter）
├── .wiki-schema.md                                   # 本文件
├── raw/
│   ├── source_manifest.json                          # 原始资料登记（canonical）
│   └── sources/                                       # 原始资料文件
├── wiki/{sources,entities,topics,comparisons,synthesis,decisions,queries,open-questions}/
├── inbox/                                            # capture 缓冲（RFC-003）
│   └── archive/{promoted,dropped}/
├── maps/                                             # 派生图谱可视化
└── .wiki/
    ├── review_queue.json                             # 待审核（canonical）
    ├── capture_policy.json                           # capture 策略（canonical）
    └── (派生层 .gitignore: id_index / inbox_index / normalized_alias_index / cache 等)
```

## 页面类型与 ID prefix

每个 wiki 页面 frontmatter 必须有 `id`，格式 `<prefix>_YYYYMMDD_<slug>`。`id` 一旦创建**永不变**（不随标题 / slug / 路径变化）。

| 类型 | 目录 | prefix | 示例 |
| --- | --- | --- | --- |
| source | `wiki/sources/` | `src_` | `src_20260526_attention-paper` |
| entity | `wiki/entities/` | `ent_` | `ent_20260526_attention` |
| topic | `wiki/topics/` | `top_` | `top_20260526_transformer` |
| comparison | `wiki/comparisons/` | `cmp_` | `cmp_20260526_rag-vs-graphrag` |
| synthesis | `wiki/synthesis/` | `syn_` | `syn_20260526_attention-overview` |
| decision | `wiki/decisions/` | `dec_` | `dec_20260526_use-lightrag` |
| query | `wiki/queries/` | `que_` | `que_20260526_what-is-rag` |
| open-question | `wiki/open-questions/` | `oq_` | `oq_20260526_cap-tradeoff` |
| inbox（非 wiki 页面） | `inbox/` | `inb_` | `inb_20260526_153012_attention-complexity` |

**source 单主键约束**：source 类型页面 `id == source_id`（与 `source_manifest.json` 中该 source 一致）。

**同日冲突**：同 prefix 同日同 slug 重名追加 `_NN` 短序号，如 `ent_20260526_attention_002`。

**slug 不是当前标题镜像**：slug 是创建时的可读提示，页面改名后 slug 不变。

## Schema Profile

默认实例没有 `.wiki-profile.json`，等价使用 base schema。base schema 由引擎 `wiki_common.BASE_SCHEMA` 定义、随 RFC 持续演进（截至当前已含到 RFC-019）：8 类 wiki 页面、inbox、source/review/capture JSON、派生层 JSON、core 字段 enum、ID 格式、alias/redirect 语义，以及 staleness / health / visibility / capture_policy 两级脱敏 / source status / ingest progress 等增量。具体演进见 [rfcs 索引](../wiki-design/rfcs/README.md)，不再手写冻结区间。

业务实例可在实例根添加 `.wiki-profile.json`，只做增量扩展：

```json
{
  "schema_version": 1,
  "profile": "risk-control",
  "description": "可选说明",
  "extra_page_types": [
    {
      "type": "case",
      "id_prefix": "case",
      "dir": "wiki/cases",
      "required_fields": ["case_id"],
      "optional_fields": []
    }
  ],
  "extra_field_enums": {},
  "extra_optional_fields": {}
}
```

约束：

- `.wiki-profile.json` 位于实例根，与 `purpose.md` 同级，进 Git；不放在 `.wiki/` 派生层目录。
- `id_prefix` 不含下划线，完整 ID 仍为 `<id_prefix>_YYYYMMDD_<slug>`。
- profile 只能新增页面类型、新字段 enum、某类型额外可选字段。
- profile 不能改 core 字段、`status`/`confidence` enum、稳定 ID 格式、source 单主键、entity alias/redirect、inbox、JSON 契约、PII 下限或派生层规则。
- `scripts/wiki_lint.py --root <instance>` 和 `scripts/wiki_graph.py --root <instance>` 读取 effective schema；缺省 `--root knowledge`。

## 标准 frontmatter（wiki/ 页面）

```yaml
---
id: <prefix>_YYYYMMDD_<slug>             # 永不变
type: source | entity | topic | comparison | synthesis | decision | query | open-question
status: draft | active | stale | archived | redirect  # redirect 仅 entity 别名薄页
confidence: low | medium | high
created: YYYY-MM-DD
updated: YYYY-MM-DD
last_verified: YYYY-MM-DD
review: true | false
source_ids: []                           # canonical 来源引用（按 ID）
related_ids: []                          # canonical 相关页引用（按 ID）
sources: []                              # 可选显示层（Obsidian wikilink）
related: []                              # 可选显示层（Obsidian wikilink）
supersedes: []                           # 替代的旧页面 ID 数组
superseded_by: []                        # 替代本页面的新页面 ID 数组
evidence_count: 0
# 仅 entity 类额外字段：
aliases: []                              # 别名字符串数组；正名页可有，薄重定向页应为空
canonical_id: null                       # null = 正名页；指向 ent_id = 薄重定向页（须 status: redirect）
# 仅 source 类额外字段：
source_id: src_...                       # 必须 == id
hash_sha256: ...
original_path: raw/sources/...
source_url: ... | null
imported_at: ISO 8601
---
```

### `review` 与可信度派生信号

`review` 是人工背书标记，不是“是否被机器处理过”：

| 取值 | 语义 |
| --- | --- |
| `false` | AI 草拟 / 自评，未经人确认 |
| `true` | 人已确认背书当前内容 |

`review: true` 严格表示“当前仍背书”。任何负反馈都必须先撤回为 `review: false`：

- 正反馈 / 复核确认：`review: true` + `last_verified = 今天`
- 负反馈为过时：`review: false` + `status: stale`
- 负反馈为不太对但仍现役：`review: false` + 下调 `confidence`，必要时进 `review_queue type: stale_claim`

lint 以 warning 形式输出两个可信度信号，不影响 exit 1 语义：

| code | 触发 |
| --- | --- |
| `STALE_PAGE` | `status: active` 且 type 有 staleness 阈值，`now - last_verified > threshold` |
| `UNVERIFIED_HIGH` | `status: active` 且 `type ∉ {source, query}` 且 `confidence: high` 且 `review: false` |

staleness 阈值是引擎 BASE_SCHEMA 常量，不走 profile 覆盖：

| type | threshold |
| --- | ---: |
| `decision` / `synthesis` / `comparison` / `open-question` | 120 天 |
| `topic` / `entity` | 365 天 |
| `source` / `query` / profile extra type | 不检查 |

`wiki_graph` 输出派生 trust 视图到 `maps/graph-insights.md` 的「知识健康度」段：trust 概览、stale 优先列表、high-unverified 列表。stale 优先列表按 `in_degree desc, out_degree desc, id` 排序；`related_ids[]` 是当前页到目标页的单向 canonical 边。

## inbox capture item frontmatter

inbox 文件不是 wiki 页面，但有自己的 frontmatter：

```yaml
---
id: inb_YYYYMMDD_HHmmss_<slug>           # 秒级时间戳
type: inbox
status: draft | promoted | dropped       # draft → archive/promoted/ 或 archive/dropped/
created: YYYY-MM-DD
captured_from: <session-id>              # 可选
confidence: low
review: true
suggested_target_type: topic | entity | decision | ...
suggested_target_title: <晋升后页面标题>
---
```

文件命名：`YYYYMMDD-HHmmss-<slug>.md`（同秒冲突追加 `-NN`）。

## JSON 契约

### `raw/source_manifest.json`

```json
{
  "version": 1,
  "sources": [
    {
      "source_id": "src_YYYYMMDD_<slug>",
      "title": "...",
      "source_type": "pdf | markdown | web | chat | image | manual | code",
      "hash_sha256": "...",
      "original_path": "raw/sources/...",
      "source_url": "..." ,
      "imported_at": "ISO 8601",
      "last_ingested_at": "ISO 8601",
      "status": "new | triaged | ingested | skipped | failed | deleted | superseded | archived",
      "summary_page_id": "src_..." ,
      "summary_page_path": "wiki/sources/..." ,
      "adapter": "local_file | web_clipper | manual | ...",
      "language": "...",
      "notes": "..."
    }
  ]
}
```

`summary_page_id` 未生成时为 `null`；已生成时**必须等于** `source_id`。

`python3 scripts/wiki_lint.py --ingest-status` 会从 `raw/source_manifest.json` 派生 ingest 进度：全量统计各 status，并把 `status: triaged` 的条目列为待 apply 清单。该模式只读 manifest，不写 `.wiki/` 派生层。

### `.wiki/review_queue.json`

```json
{
  "version": 1,
  "items": [
    {
      "id": "rev_YYYYMMDD_NNN",
      "type": "contradiction | duplicate | missing_page | confirm | suggestion | source_gap | stale_claim",
      "title": "...",
      "status": "pending | resolved | dismissed",
      "priority": "low | medium | high",
      "source_ids": ["src_..."],
      "affected_page_ids": ["ent_...", "top_..."],
      "evidence": [
        {
          "page_id": "ent_...",
          "page_path": "wiki/entities/...",
          "quote": "...",
          "note": "..."
        }
      ],
      "options": [
        { "label": "...", "action": "snake_case_action" }
      ],
      "created_at": "ISO 8601",
      "updated_at": "ISO 8601",
      "resolved_at": null,
      "resolved_action": null
    }
  ]
}
```

`affected_page_ids` / `evidence[].page_id` 是 canonical；`evidence[].page_path` / `source_paths` 是显示层。

### `.wiki/capture_policy.json`

```json
{
  "version": 1,
  "auto_capture": false,
  "default_visibility": "private",
  "hard_redact": {
    "patterns": [
      "AKSK / token / password / 密钥 / 私钥 / 连接串 / private key 等硬底线正则"
    ]
  },
  "soft_redact": {
    "patterns": [
      "客户信息 / 邮箱 / 手机 / IP 等按库可配置软项正则"
    ]
  },
  "exclude_paths": [],
  "max_inbox_files": 100,
  "updated_at": "ISO 8601"
}
```

`visibility` 是 wiki 页和 `source_manifest.sources[]` 的 core optional 字段，取值 `public | internal | private`；缺失时 effective visibility = 显式字段 → `capture_policy.default_visibility` → legacy `private`，lint 不写回字段。

脱敏分级：`hard_redact` 命中为 error，任何库都不可放宽；`soft_redact` 命中为 warning，可按库配置，`visibility: public` 时仍保持 warning 以提醒公开前确认。旧版 `exclude_patterns` 仍被 lint 接受为 `soft_redact` legacy alias，并产生 `CAPTURE_POLICY_LEGACY` warning。

⚠ **默认正则仅是初始规则，不代表完整 PII 检测**。生产用法必须由 lint、人工 review 和组织安全规范共同保障。Agent 不得把这套正则当作唯一 PII 兜底。

## Ingest 子链接约定

源文档正文里的子链接由写入 AI 在 ingest 时处理；现有规范工具不把原始抓取内容或完整子链接清单作为契约输入，因此不能机械证明"所有子链接都已发现"。工具只校验已经落到 wiki / JSON 正本里的结构和引用完整性。

处理规则：

- 内部文档链接：脱掉 token / 内部 URL，但保留"父文档链向 X 文档"的语义事实。目标值得收时建子 source；正文未抓到时，子 source 用 `status: draft` + `confidence: low` 占位，父 source 用 `related_ids` + `related` 关联子 source。
- source-gap：只有链接与当前 source 的知识内容相关，且目标未抓到或未 ingest 时才建；导航、页脚、泛工单入口、广告、站点通用帮助入口等弱相关链接不做。
- 外部链接：正文只保留脱敏后的外链说明，不建 source、不跟进。
- 不递归：不自动跟内链 / 外链继续 ingest；用户显式要求补抓某个子文档时，作为新的独立 ingest。

### Source-gap Open Question

长期保留的子链接缺口使用 `wiki/open-questions/*-source-gap.md`：

```yaml
---
id: oq_YYYYMMDD_<slug>-source-gap
type: open-question
status: active
confidence: medium
created: YYYY-MM-DD
updated: YYYY-MM-DD
last_verified: YYYY-MM-DD
review: false
source_ids:
  - src_<parent-source>
  - src_<child-source-placeholder>
related_ids:
  - src_<parent-source>
  - src_<child-source-placeholder>
sources:
  - [[parent-source-slug|父 source 标题]]
  - [[child-source-slug|子 source 标题]]
related:
  - [[parent-source-slug|父 source 标题]]
  - [[child-source-slug|子 source 标题]]
supersedes: []
superseded_by: []
evidence_count: 1
---

# <子文档标题> 正文待补抓

## 已知信息

- 父 source 在何处提到该子文档。
- 当前对子文档已抓到的标题、修改时间、分享人、截图或其它元信息。

## 待确认

- 缺什么正文 / 图片 / 权限 / 登录态。
- 为什么当前没有抓到，以及补抓需要什么条件。
```

补抓完成后，把对应 source-gap open-question 标为 `status: archived`，并在正文记录收尾结果。`review_queue.type: source_gap` 仍可作为 ingest / triage 阶段的临时结构化队列或人工审查入口；一旦决定把缺口作为长期待办保留，应晋升为 `wiki/open-questions/*-source-gap.md`，使其进入图谱、查询和回答阶段。

## Ingest 批量编排约定

批量 ingest 使用 manifest status 作为单一真相，不另建队列文件：

1. Triage 可以全量执行，但必须是轻扫：目录、文件名、元信息、标题、hash、source_type、粗摘要或占位、alias 候选和 manifest 登记；不要读完所有长正文，不做图片多模态，不写详细 source 正文。
2. Triage 产物写入 `raw/source_manifest.json`，新条目使用 `status: triaged`，`summary_page_id: null`，`summary_page_path: null`。
3. Apply 清单来自 `python3 scripts/wiki_lint.py --ingest-status` 的 ingest 进度段；只有 `triaged` 进入待 apply。
4. Apply 必须逐份深入；只有短小且同质的材料可一批最多 3 份。含图、子链接或长正文的材料必须逐份。
5. 状态转换顺序固定：`triaged` → 写完 wiki 正本并跑 lint 通过 → `ingested` + commit。失败时改 `failed`，在 `notes` 记录原因和下一步。
6. 每份 source 完成后单独 commit。新会话续传时先看 `--ingest-status`，不要从聊天记忆推断剩余工作。

## 富媒体引用约定

原始图片证据落在 `raw/sources/assets/`，由 ingest / 写入 AI 负责生成语义描述和必要的关键文字摘录；工具链只做文本和路径校验，永不读取图像像素。

wiki 正文引用图片使用相对 Markdown 图片链接：

```markdown
图 001：![简短 alt](relative-path-to-raw-sources-assets/example.png)

这张图展示了……
```

实际路径从引用页所在目录计算到 `raw/sources/assets/`；例如 `wiki/topics/` 下的页面需要回到实例根后再进入 `raw/sources/assets/`。

lint 会先剥离代码块，再检查 `![alt](path)` / `![[path]]`：

- `http://`、`https://`、`data:`、`mailto:` 视为非本地引用，跳过断引校验。
- 本地路径按引用页所在目录解析，归一化后必须仍在实例根内，且目标文件必须存在。
- 图片文件名、相对路径、紧邻描述文本、`source_manifest.json` 中的 notes / caption 类文本会按 `capture_policy.hard_redact` 扫描，命中为 error。
- 缺少同一行或随后 3 行内的描述文本时产生 `IMAGE_NO_DESCRIPTION` warning。

## Cross-ref canonical 边界

**canonical**（lint 严格校验、按 ID）：

| 位置 | 字段 |
| --- | --- |
| 页面 frontmatter | `id`、`source_ids`、`related_ids`、`supersedes`、`superseded_by`、`canonical_id` |
| `review_queue.json` 单条 item | `affected_page_ids`、`evidence.page_id` |
| `source_manifest.json` 单条 source | `summary_page_id` |
| 未来 `maps/graph-data.json` 节点 key | 页面 `id` |

**显示层**（仅给人看，lint 不校验完整性）：

| 位置 | 字段 |
| --- | --- |
| 页面 frontmatter | `sources`、`related`（wikilink） |
| `review_queue.json` 单条 item | `evidence.page_path`、`source_paths` |
| `source_manifest.json` 单条 source | `summary_page_path` |
| 答案引用里的 `wiki/.../X.md` 字符串 | 可读 path |

## 答案引用格式

```markdown
正文用 [1]、[2] 标注关键判断。

## 引用

- [1] [[example|页面名]] · `wiki/topics/example.md` · 支撑：一句话说明
- [2] [[source-summary|来源摘要]] · `wiki/sources/x.md` · 原始资料：`raw/sources/x.pdf` · source_id: `src_...`

## 置信度与缺口

- 置信度：medium
- 还需要验证：...
```

**别名引用规则**：用户用别名时，回答保留别名原写法并附正名 wikilink，**不要**把别名包成 wikilink：

- 正确：`self-attention（正名 [[attention|Attention]]）`
- 错误：`[[self-attention]]（正名 [[attention|Attention]]）`（除非别名薄页确实存在）

## 写入规则

- 普通对话：默认只读，不写 `wiki/` 正本；若识别到值得暂存的内容，按 RFC-003 capture 建议模式在回答末尾提示 `💡 建议 capture：...`。
- crystallize：用户明确说"沉淀 / 整理 / 整理进知识库 / 消化这篇资料 / 结晶化 / 更新 Wiki"时，直接按 schema 写 `wiki/` 正本，不必先过 inbox。
- capture：用户说"存" / "capture" / "记到 inbox"，或 `capture_policy.json` 的 `auto_capture: true` 时，写 `inbox/` 缓冲层，不直接进 `wiki/`；每次写入必须可见报告（`✏️ 已 capture：...`）。
- PII 兜底：内容含密钥 / 客户姓名 / 内部业务等，**无论 auto_capture 开关**一律降级为建议模式。脱敏分两级——`hard_redact` 命中为 error（硬底线，任何库不可放宽），`soft_redact` 命中为 warning（可按库配置）；另有 `visibility`（`public`/`internal`/`private`，缺失继承 `default_visibility`）。权威定义见上文「Capture Policy」段的 `capture_policy` JSON 与实际 `.wiki/capture_policy.json`；旧 `exclude_patterns` 仅作 `soft_redact` 的 legacy alias。
- **严禁绕过 inbox 直接写 `wiki/`** 仅约束 capture 路径：不得把"随手记"直接写成正本；不约束 crystallize。

## 拆分与合并语义

- 拆分：新页面拿新 ID；旧页面若保留则原 ID 不变；若完全被取代标 `status: archived` + `superseded_by: [新 ID]`。
- 合并：被合并页保留壳 frontmatter，`status: archived` + `superseded_by: [合并目标 ID]`，正文清空或留一行重定向说明。

## entity 别名机制

99% 别名应放在正名页的 `aliases` 列表里，不建薄页。

少数情况（外部已有 wikilink 散布、不便迁移）才建薄重定向页：`canonical_id` 指向正名页 `id`，`status: redirect`，不参与主图谱节点 / 综合 / 引用来源。

`normalized_alias_index.json` 维护规范化匹配（大小写 / 空格 / 连字符 / 中文全/半角 / 复数）。

## Inbox 晋升 workflow

